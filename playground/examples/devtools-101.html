Walkthrough

First impression. Checkboxes work. Filter works. Theme switcher works. The code is 100 lines, no console errors, no obviously-expensive expressions. If this landed in review you'd probably approve it. Let's see what the runtime says.

1 — What is really wired to a node?

Open Inspect on the rail, hit Pick an element, click any priority badge.

You get two bindings — the vln-text and the vln-class — with their current values, reads, and the mutation that last changed each read. Look at the badge's vln-class: it reads two paths, task.priority and theme. The second one isn't typed anywhere obvious — it's hiding in the template string 'theme-badge-' + theme, and every row's badge is now subscribed to the global theme.

Takeaway: Inspect replaces grepping for directives and guessing what each binding reads. The reads chips drill into Query for who else depends on each path.

2 — The sluggish theme switcher

Open Record, hit Record, toggle the theme dropdown three times, hit Stop.

The top row is the badge's vln-class expression. It ran 3 × (number of visible rows) times. One state change, N re-renders — a sibling fan-out. Click the row to drill into Explain: the reads chips show both theme and task.priority; why did this run shows theme as the triggering path.

Root cause: the theme-badge-X class is stamped on every row because, in the moment of writing the template, it was easier to compose the class string than to think about CSS cascade (devtools-101.html line 36). The theme is a single switch sitting on an ancestor already — nothing downstream needs to re-read it. Fix: delete the per-row theme class entirely and let CSS inherit from the parent. One reactive dep on the container, zero on the rows: 

// before — devtools-101.html line 37
<span vln-class="'priority-' + task.priority + ' theme-badge-' + theme"></span>

/* and the CSS */
.theme-badge-light { background: #e5e7eb; }
.theme-badge-dark  { background: #374151; color: #f3f4f6; }
.theme-badge-hc    { background: #fff; color: #000; outline: 1px solid #fff; }
// after — no theme class on the row at all
<span vln-class="'priority-' + task.priority"></span>

/* and the CSS — descend from the already-themed container */
.theme-light .priority-high,
.theme-light [class^="priority-"] { background: #e5e7eb; }
.theme-dark  [class^="priority-"] { background: #374151; color: #f3f4f6; }
.theme-hc    [class^="priority-"] { background: #fff; color: #000; outline: 1px solid; }

The lesson isn't about Velin, it's about styling. A theme is a global variable — treat it like one. Set it once on an ancestor and let the cascade do the propagation CSS was designed to do, instead of templating the same value into N descendants and asking the reactive system to re-render them in lockstep.

3 — The innocent-looking stat line

See the gray N tasks · M done · state size line? Looks like a cheap counter. Record, toggle one checkbox, Stop.

debugLine ran once — expected. Drill into it. The reads chips are a mile long: tasks[0].title, tasks[0].done, tasks[0].priority, tasks[1].title… every field of every task. Toggling one checkbox re-serializes the entire list.

Root cause: JSON.stringify(this.tasks) inside the getter (devtools-101.js line 41). Velin's tracker records every property observed during the getter run — stringify walks everything, so the effect takes a dep on everything. Fix: compute what you'll actually display, nothing more: 

// before — devtools-101.js line 40
get debugLine() {
  const serialized = JSON.stringify(this.tasks);
  const doneCount  = this.tasks.filter((t) => t.done).length;
  return `${this.tasks.length} tasks · ${doneCount} done · state size: ${serialized.length}b`;
}
// after — reads tasks.length and tasks[i].done only
get debugLine() {
  const doneCount = this.tasks.filter((t) => t.done).length;
  return `${this.tasks.length} tasks · ${doneCount} done`;
}
4 — Mutation loops need batches

Record, click ✓ all done, Stop. The results show filteredTasks and debugLine each firing N times, with total ms well above a single-run cost. The driver column pins it on tasks[i].done, N distinct paths.

The source is a plain for loop assigning t.done = true (devtools-101.js line 59). Nothing looks wrong. The problem is that each assignment synchronously flushes every dependent effect — so N writes = N × every-effect-that-reads-tasks.

Fix: wrap the loop in a batch(). The mutations still happen one by one, but effects run once at the end: 

// before — devtools-101.js line 57
markAllDone() {
  for (const t of this.tasks) t.done = true;
}
// after — one flush, same semantics
markAllDone() {
  Velin.getController(this).batch(() => {
    for (const t of this.tasks) t.done = true;
  });
}
5 — Signals catch the same bug at scale

Click load 500. The UI hangs for a beat and the badge in the corner tints amber: the hook emitted a thrash signal because tasks was mutated more than 32× in one animation frame.

Click the badge. The Signals inbox opens with each signal explained (what / why / what to do). From any entry you can drill into Explain to see the effect's recent runs, its reads, and the paths that triggered it.

Root cause: loadDemo is exactly the same shape as the pre-fix markAllDone from step 4 — a plain loop doing 500 synchronous writes (devtools-101.js line 65). Every push re-runs every effect that reads tasks: the loop re-renders, debugLine re-serializes, every row's vln-loop recomputes. Fix: the same batch pattern: 

// before — devtools-101.js line 63
loadDemo() {
  const start = this.tasks.length;
  for (let i = 0; i < 500; i++) {
    this.tasks.push({ id: this.nextId++, title: rndTitle(start + i), ... });
  }
}
// after — one flush instead of 500
loadDemo() {
  Velin.getController(this).batch(() => {
    const start = this.tasks.length;
    for (let i = 0; i < 500; i++) {
      this.tasks.push({ id: this.nextId++, title: rndTitle(start + i), ... });
    }
  });
}

The lesson: Signals are a passive tripwire. You don't have to Record, you don't have to go looking — when something crosses a threshold (thrash, long-effect, orphan-spike) the badge counts it and the inbox explains it. In practice this catches the same class of bug step 4 taught, but surfaces it without you remembering to look.

6 — Did anything stick around after it closed?

Click details on any task, close the modal (Esc or the close button), repeat five times. Everything feels normal — the modal is gone, no visible residue.

Open Leaks, hit Run scan. Detached state roots and Detached effects are both non-zero and growing with every open+close.

Root cause: openDetails mounts a nested Velin.bind() on an overlay <div>, and the close handler only calls overlay.remove() (devtools-101.js lines 90–104). The DOM is gone, but the state tree, its bindings, and every effect those bindings created are still alive and still subscribed to the parent. Fix: pair every bind() with an unbind(): 

// before — devtools-101.js close handler + Esc handler
close() {
  overlay.remove();
}
// …
const onKey = (e) => {
  if (e.key !== "Escape") return;
  document.removeEventListener("keydown", onKey);
  overlay.remove();
};
// after — unbind before you drop the DOM
close() {
  Velin.unbind(nestedState);
  overlay.remove();
}
// …
const onKey = (e) => {
  if (e.key !== "Escape") return;
  document.removeEventListener("keydown", onKey);
  Velin.unbind(nestedState);
  overlay.remove();
};
7 — What else watches this path?

Open Query, path theme, scope wide, Run. The results list every effect that would re-run if you changed the theme, grouped by node, with the estimated ms cost. Narrow mode asks: effects on this state that read this exact path. Wide mode descends into composed children — every row's own state.

Why this matters: iteration dependencies aren't visible to source grep — a row that reads task.priority doesn't type theme anywhere, but still subscribes to it via the composed template string. Query is how you answer if I rename this path, what breaks? before you break it.
